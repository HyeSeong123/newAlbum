# 감자싹 개발 단계 경량 검증 및 출시 전 QA 정책

> 기준 브랜치: `final` · 적용일: 2026-10-24  
> 목적: 정식 출시 전에는 **기능 구현 속도와 Android 사용성**에 집중하고, Work 탭의 불필요한 전체 검사·반복 분석·대량 로그 출력을 줄인다. 사용자 데이터와 보안에 직결되는 위험은 개발 단계에서도 즉시 검증한다.

## 1. 두 가지 운영 모드

| 모드 | 적용 시점 | 검증 원칙 |
| --- | --- | --- |
| **개발 모드(기본값)** | 기능 개발·버그 수정·디자인 조정 | 변경 코드와 영향 화면만 확인. 실제 버튼 동작, 상태·저장 결과, Android 배치를 우선한다. |
| **출시 검증 모드** | 사용자가 정식 출시 준비 또는 전체 검증을 요청할 때 | 전체 회귀·빌드, 주요 화면, 보안·성능, Android 설치·업데이트·오프라인·데이터 보존을 종합 점검한다. |

개발 모드라고 해서 테스트를 아예 생략하지 않는다. **수정한 기능이 실제로 동작하는지 확인하는 최소 검증**은 필수다. 실행 환경이 없어 확인하지 못한 항목은 통과가 아닌 **미검증**으로 보고한다.

## 2. 변경 유형에 따른 개발 모드 검사 범위

| 변경 유형 | 우선 실행하는 검사 | 개발 중 상시 실행하지 않는 검사 |
| --- | --- | --- |
| 문서·주석만 변경 | 문서 내용, 상대 경로, 정책 충돌 확인 | 앱 빌드·전체 UI·보안 스캔 |
| CSS·화면 배치·도움말 변경 | 변경 화면의 모바일 전후 비교, 실제 버튼 클릭, 스크롤·가려짐·닫기/뒤로가기, 필요한 타입/빌드 확인 | 전 화면 시각 회귀, 모든 플랫폼 설치 검사 |
| 일반 기능·상태 관리 변경 | 수정 기능의 성공·실패/취소 경로, 관련 단위·브라우저 테스트, 저장/재진입 확인 | 관련 없는 AI·DB·Windows 전체 검사 |
| 사진·파일·SQLite·권한·삭제·마이그레이션 변경 | 관련 데이터 보존·파일 무결성·실패 복구·권한 검사, 관련 저장소 테스트 | 해당 안전 검사를 출시 시점으로 미루지 않음 |
| 의존성·보안 경계·개인정보·서명·AI 모델/라이선스 변경 | 해당 위험의 보안·호환성·라이선스 검사와 관련 기능 회귀 | 위험을 무시한 일괄 검사 생략 |

- 검증 단위는 **개별 버튼 또는 변경한 사용 시나리오**다. 검증 없이 '정상'이라 쓰지 않는다.
- 타입 검사와 빌드는 코드 변경 묶음이 마무리될 때 가급적 1회 수행한다. 작은 CSS 수정마다 전체 테스트를 반복하지 않는다.
- 이미 GitHub Actions에서 확인한 검사와 동일한 전체 검사를 Work가 다시 수행하지 않는다. 다만 실패 원인 확인 및 수정 검증은 수행한다.
- 앱 동작을 바꾸지 않은 문서 전용 커밋에는 Android 설치나 앱 화면 캡처를 요구하지 않는다.

## 3. 디자인과 실제 동작의 최소 UX 검증

기획자와 일반 사용자 관점을 모두 적용하되, 개발 모드에서는 **변경한 화면에 대한 짧은 점검**으로 제한한다.

- **기획자:** 버튼 이름만으로 결과를 예상할 수 있는가? 중요 버튼의 위치·우선순위·용어·캐릭터 도움말·디자인 토큰이 일관적인가?
- **일반 사용자:** 설명 없이 누를 수 있는가? 클릭 후 화면 반응·실제 결과·취소/뒤로가기·재시도 동작이 기대와 일치하는가?
- **Android 우선:** 작은 세로 화면에서 터치 영역, 하단 안전 영역, 키보드, 스크롤, 팝업 고정, 가로 넘침, 콘텐츠 가림을 확인한다. Windows는 영향을 받은 경우에 검증한다.
- **화면 변경 시:** 가능한 경우 같은 상태·화면 크기의 수정 전/후 캡처를 비교하고, 실제 클릭으로 해당 흐름을 테스트한다. 브라우저 에뮬레이션을 Android 실기기 검증이라고 표현하지 않는다.
- **버튼 검증 기록:** `누르기 전 상태 → 누른 동작 → 표시되는 반응 → 변경·저장된 결과 → 취소·오류 복구`를 필요한 만큼만 기록한다.
- 기존 사진·앨범·일기·인물·반려동물 연결은 보존한다. 테스트는 별도 샘플 데이터를 우선 사용한다.

## 4. Work 탭 실행 규칙 (토큰 사용 최소화)

1. 시작할 때 `AGENTS.md`, 현재 `final` HEAD·열린 PR, 관련 문서·소스를 확인한다. 같은 작업 내에서 변화가 없다면 불필요하게 다시 읽지 않는다.
2. 관련 파일과 변경점 위주로 분석한다. 작은 수정에 전체 저장소 감사, 무관한 모델 분석, 대량 리팩터링을 덧붙이지 않는다.
3. 실제 코드를 수정한 뒤 **변경된 기능 중심**으로 검증한다. 관련 테스트가 없으면 가능한 범위에서 작은 재현·검증 시나리오를 추가한다.
4. 로그는 실패 부분·핵심 결과만 확인한다. 전체 빌드 로그와 테스트 원문을 반복 출력하거나 같은 검사를 습관적으로 재실행하지 않는다.
5. GitHub Actions가 이미 수행하는 검사는 CI 결과를 확인하고 중복 실행을 피한다. **현재** `.github/workflows/source-validation.yml`은 `docs/**` 변경에도 검증을 실행한다. 이 문서는 기존 CI 트리거를 변경하지 않는다.
6. 코드·UI 변경을 하지 않은 문서 작업은 문서 자체를 확인하면 된다. UX 전후 캡처나 실제 앱 클릭 검사를 수행했다고 보고하지 않는다.

기존 프로젝트에서 확인된 명령 예시는 다음과 같다. **모두 매번 실행하라는 뜻은 아니다.**

```bash
# 관련 TypeScript만 빠르게 점검할 때
npx tsc --noEmit

# 화면 관련 테스트는 필요한 파일만 Android 크기의 브라우저 프로젝트로 선택
npx playwright test tests/help-spotlight.spec.ts --project mobile

# 소스 수정 묶음을 마무리할 때 (TypeScript + Vite + 빌드 검증 포함)
npm run build

# 상태·모델 관련 수정이 있어 전체 프런트 단위 검사가 필요한 경우
npm run test:unit
```

실제 테스트 파일과 프로젝트 설정이 다르면 현재 저장소를 기준으로 명령을 조정한다.

## 5. 출시 검증 모드의 필수 점검

사용자가 출시 검증을 요청하면 영향 범위만이 아닌 제품 전체를 대상으로 다음 항목을 확인한다.

1. 프런트엔드 타입 검사·프로덕션 빌드·주요 단위·E2E·Rust/SQLite 회귀 검사 및 CI 결과.
2. 주요 화면의 Android 터치·반응형·접근성·도움말·뒤로가기·실패 복구와 Windows 영향 범위.
3. Android APK 설치·앱 업데이트·앱 재시작·오프라인 사용·기존 사용자 데이터 마이그레이션 및 보존. 에뮬레이터와 실기기는 구분한다.
4. 사진 원본 보존, 파일 삭제 범위, 인물·반려동물·일기·앨범 연결, DB 롤백·오류 복구.
5. 의존성·비밀정보·권한·개인정보·파일 접근·모델 상업적 이용 권리 등 보안/라이선스 검사.
6. 시작 속도·대량 사진·메모리 등 사용자 체감 성능과 Android 앱 서명 인증서·기존 설치본의 업데이트 호환성.

보안 또는 데이터 손실 가능성이 있는 변경은 출시 검증 모드가 아니어도 **즉시 관련 항목을 검사**한다. 검증되지 않은 항목이 남으면 출시 합격으로 표시하지 않는다.

## 6. 보고 형식

완료 보고서는 길고 반복적인 감사 보고서 대신 다음을 간결하게 기록한다.

- **변경:** 파일, 핵심 수정 내용, 브랜치·커밋 또는 PR.
- **기획자/사용자 확인:** 변경된 화면에서 예상 동작과 실제 관찰 결과.
- **검증:** `통과` / `실패` / `미검증`을 명확하게 구분. 수행한 명령과 CI 근거.
- **시각 확인:** 화면 변경이 있었다면 전후 차이, Android 화면·버튼 클릭 확인 여부.
- **남은 위험:** 실제 Android 설치·실기기·Windows·전체 회귀 등 이번에 하지 않은 검사와 이유.

문서만 수정했다면 앱 실행·UI 변경·버튼 확인은 **해당 없음/미수행**으로 표시한다. 테스트 로그가 없는데 결과를 추정해 통과로 기록하지 않는다.

---

이 정책은 루트 `AGENTS.md`의 데이터·서명키 보존, 두 페르소나, 실동작 검증 원칙을 **대체하지 않고 검사의 빈도와 범위를 구체화**한다. 사용자가 명시적으로 요청한 테스트 범위 및 안전상 필요한 검사를 우선한다.
