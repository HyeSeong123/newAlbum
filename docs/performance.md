# 소스·DB 성능 개선 (2026-09-27)

`feature/warm-journal-v2`, 기준 커밋 `c3dcfa9`의 실제 반복 작업을 줄인 변경이다.
기존 화면 디자인, Tauri 명령 인자/응답, 원본 파일, 저장소 키를 유지한다.
모든 화면이 동일한 비율로 빨라진다는 의미는 아니다.

## DB 연결과 마이그레이션

- 기존 앱은 **모든 DB 연결**에서 스키마 DDL, 컬럼 검사, 전체 미디어 경로
  읽기/정규화를 실행했다. 이제 `database::initialize`에서 `user_version`을
  확인하고 현재 버전이면 즉시 반환한다.
- 이전 사용자 DB의 버전 0과 새 DB 모두 버전 1로 이전한다. 기존 마이그레이션과
  새 인덱스를 `IMMEDIATE` 트랜잭션 안에서 적용하고 마지막에 버전을 기록한다.
  실패 시 컬럼·데이터·버전 모두 롤백한다. 동시에 들어오는 초기 명령은
  쓰기 잠금 획득 후 버전을 다시 확인한다.
- 매 연결의 외래키 검사와 5초 잠금 대기는 유지한다. 저널 모드나 동기화
  내구성 설정을 낮추지 않으며 자동 VACUUM/원본 변경은 수행하지 않는다.
- 앞으로 스키마를 바꿀 때는 `VERSION` 증가와 순차 마이그레이션이 필요하다.
  `schema.sql` 수정만으로 기존 DB에 반영되지 않는다. 더 높은 DB 버전은
  이전 버전 앱에서 변경하지 않고 업데이트 안내 오류를 반환한다.

## 쿼리와 파일 작업

- 미디어 정렬 인덱스로 별도 임시 정렬을 없앴다. 전체 미디어를 가져오는
  현재 API의 반환량 자체는 바꾸지 않았다.
- 앨범 항목, 표지, 얼굴, 반려동물, 태그/인물의 역방향 외래키 인덱스를 추가했다.
  사진 삭제 시 연결 테이블 전체를 반복해서 찾는 비용을 줄인다.
- 다중 사진 삭제는 준비된 문장과 한 트랜잭션으로 처리한다. 중간 오류 시
  일부만 삭제하지 않는다. 기존 표지 교체 트리거와 FK 처리는 유지한다.
- 위치 분석은 최대 24개 파일을 잠금 밖에서 읽고 결과를 한 번에 저장한다.
  다른 작업에서 이미 처리한 행은 `location_status='queued'` 조건으로 보호한다.
- 반려동물 목록은 개체마다 조회하던 연결 사진을 한 번에 읽는다. 빈 목록과
  기존 정렬을 유지한다.
- 폴더 탐색·파일 해시·EXIF를 포함한 등록 작업은 blocking 작업 스레드에서
  실행한다. 앨범 목록 조회와 다중/전체 삭제도 작업 스레드에서 처리한다.
  파일 I/O 전체를 긴 DB 쓰기 트랜잭션으로 감싸지 않는다.
- 기존 사진의 누락된 크기 보완은 라이브러리 불러오기에서만 수행한다.
  삭제·등록 응답의 `read_media`는 파일을 열지 않는다. 누락/지원하지 않는
  파일은 다음 라이브러리 불러오기 때 다시 확인할 수 있다.

## 프런트

- 추억 지도 컴포넌트·GeoJSON·CSS를 메뉴 진입 시 불러온다. 지도 미사용 시
  경계 JSON 파싱과 SVG 경로 생성도 실행되지 않는다.
- 브라우저 미리보기의 지역 집계를 지역별 반복 필터에서 단일 순회로 변경했다.
  데스크톱에서는 이 집계를 실행하지 않고 DB 집계를 사용한다.
- 월별 묶음은 누적 배열 복사 없이 만들고 지도 hover에서 재계산하지 않는다.
- 앨범 미디어 동기화는 변하지 않은 앨범/항목 배열을 재사용한다. 수정된 항목만
  교체하고, 삭제 반영과 아직 로딩 중인 앨범의 사진 보존은 유지한다.

## 재현 가능한 측정

Linux 작업 환경, Node 24, Vite production build의 초기 JS:

| 항목 | 이전 | 이후 |
| --- | ---: | ---: |
| 초기 JS | 588.36 KB | 370.56 KB |
| 초기 JS gzip | 189.05 KB | 111.71 KB |
| 지도 지연 로딩 JS | 초기 번들에 포함 | 218.54 KB |

초기 JS 약 37%, gzip 약 41% 감소. 총 다운로드량 감소와 구분해야 한다.
지도 진입 시 해당 청크가 추가로 로드되며 기존 얼굴/반려동물 추론 청크는 유지한다.

`python scripts/benchmark-database.py`로 임시 DB를 만들고 제거한다.
SQLite 3.53.1, 사진 20,000건, 앨범 100개와 얼굴/반려동물 연결 자료,
5회 중앙값 예시:

| 항목 | 이전 | 이후 |
| --- | ---: | ---: |
| 100건 삭제 + FK 확인, rollback | 364.873 ms | 11.613 ms |
| 전체 미디어 메타데이터 정렬 조회 | 46.918 ms | 45.679 ms |
| 연결 시 전체 경로 읽기 / 버전 읽기 | 9.043 ms | 0.005 ms |

삭제 비교는 양쪽 모두 트랜잭션을 사용해 인덱스 효과를 비교한다. 마지막 행은
두 SQL 작업 자체의 비교이며 전체 연결/앱 시작 시간은 아니다. 전체 목록 조회는
큰 시간 개선을 주장하지 않는다. 테스트 DB에서 추가 인덱스 공간은 약 1.41 MB이며
원본 사진 크기와 무관하다. 사용자 환경의 저장장치·자료 분포에 따라 결과가 달라진다.

## 검증 방법

- `npm run test:unit`: 기존 모델과 앨범 객체 재사용, 지도 집계/월 묶음 테스트.
- `npm run build`: TypeScript 검사와 production 청크 확인.
- `cargo test --manifest-path src-tauri/Cargo.toml --lib --locked`: 새/기존 DB 이전,
  재실행, 동시 초기화, 이전 실패/삭제 실패/분석 저장 실패 롤백, FK 정합성,
  인덱스 사용 계획, 기존 사진·앨범·얼굴·반려동물 기능 검증.
- Linux에서는 `RUSTUP_TOOLCHAIN=stable`과 GTK/WebKit 개발 패키지가 필요하다.
  Tauri 테스트 매크로에 필요한 `icons/icon.png`는 기존 ICO에서 임시 생성하고
  테스트 후 제거한다. Windows 실행파일 생성·설치·실행 검증은 하지 않는다.
- 기존 Playwright 사진 상세·앨범·추억·지도·타임라인 흐름과
  `python -m unittest discover -s tests -p test_album_storage.py`를 유지한다.

실제 사용자 DB/원본 파일에는 접근하지 않는다. UI 전체 가상화, 썸네일 정책 변경,
전체 목록 API 페이지네이션은 실제 대형 라이브러리 프로파일링 후 별도 검토한다.

참고: [SQLite user_version](https://www.sqlite.org/pragma.html#pragma_user_version),
[외래키 인덱스](https://www.sqlite.org/foreignkeys.html#fk_indexes).

## 대용량 가져오기 진행 표시 (v0.5.4)

- 파일 선택, 폴더 탐색, 파일 등록, 지역 저장, 앨범 생성과 결과 정리까지 전체 화면 로딩을 유지한다. 진행 중에는 배경 화면의 클릭과 키보드 입력을 막고 완료·취소·실패 때 해제한다.
- 네이티브 등록은 기존 작업 스레드와 중복 해시를 유지한다. Tauri Channel로 현재 파일, 처리 개수, 해시 계산 중 읽은 바이트를 전달한다. 큰 영상 하나를 처리하는 동안에도 약 100ms 간격으로 용량이 갱신된다. 진행률은 실제 읽은 용량이며 남은 시간을 추정하지 않는다.
- 브라우저 등록은 선택 목록을 먼저 복사한다. 파일 입력을 초기화해도 목록이 사라지지 않으며 128개씩 처리하고 화면을 갱신할 시간을 준다. 중복 파일의 URL은 만들지 않고 중간 실패 시 생성한 URL을 모두 해제한다.
- 지역 저장과 앨범 생성이 끝나기 전에 등록 잠금을 해제하지 않는다. 중간 등록 실패 시 저장된 기록을 다시 읽어 보존하고 실패 원인을 표시한다.
- 가져오기 Playwright 검사는 큰 영상의 용량 진행, 전체 화면·키보드 잠금, 지역·앨범 처리, 선택 취소, 브라우저 입력 초기화, 실패 후 재시도를 데스크톱과 모바일에서 확인한다. 네이티브 해시 검사는 기존 FNV 값과 최종 읽은 바이트를 확인한다.
